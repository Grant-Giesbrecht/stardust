- `dict_to_tome` leaves a lot of dead space in the HDF5 file even on a single fresh write (`h5py.File(save_file, 'w')` — not a case of stale slack carried over from a previous save on the same path). Found investigating why a real GrAF file with ~20 data points was 1.27 MB: `h5stat` accounts for only ~65 KB of live object headers/B-trees/data across its 129 datasets + 21 groups, and running `h5repack` on it losslessly shrinks it to 60,388 bytes (21x smaller, same structure, verified readable). Byte-inspected the gap directly: ~98% of the extra ~1.2 MB is literal zero padding, the rest is small non-zero fragments. Not yet root-caused inside `dict_to_tome`/`_write_tome_dict` (no delete/require-then-recreate pattern was found there on a read of the write path, so the leak is presumably from HDF5's own default file-space allocation behavior — strategy `FSM_AGGR`, non-persistent free-space tracking — during the many small group/dataset creations that one write does, not from anything obviously wrong in the calling code). Worth a closer look at whether `h5py.File`'s file-creation-property-list defaults (file space strategy/page size) are doing something coarser than intended for a format that's deliberately "one dataset per scalar field." Proposed fix: have `dict_to_tome` repack after writing (either shell out to `h5repack`, or write through a second fresh `h5py.File` copy, or set a `PAGE` file-space strategy with `persist=True` and a small threshold at file creation) so callers never see this bloat.
